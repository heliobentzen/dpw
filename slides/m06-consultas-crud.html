01

Do array ao banco

O AcervoService ainda é o do M03. Ele muda; o controller, não.

Mão na massa · acervo.service.ts

Pedir ao Nest o repositório

@Injectable()
export class AcervoService {
  constructor(
    @InjectRepository(Obra) private readonly obras: Repository<Obra>,
    @InjectRepository(Autor) private readonly autores: Repository<Autor>,
  ) {}
}

@InjectRepository(Obra): a injeção do M03, com um decorator a mais para dizer de qual entidade.

Repository<Obra>: o genérico dá tipo ao retorno — find() devolve Obra[], não any[].

Só funciona porque as entidades estão no forFeature (M04). Senão: can't resolve dependencies.

O repositório de Autor serve para demonstrar o N+1, na seção 03.

E apague o @Get("nome")
Endpoint temporário que sobrevive ao módulo vira permanente por acidente.

Ele já provou que o ConfigService funcionava. Em três meses, ninguém saberia se pode remover.

Mão na massa · listar

Paginado desde o começo

async listar(pagina = 1, tamanho = 20) {
  const [itens, total] = await this.obras.findAndCount({
    relations: { autor: true },
    order: { titulo: "ASC" },
    skip: (pagina - 1) * tamanho,
    take: tamanho,
  });
  return { itens, total, pagina, tamanho };
}

Valores padrão: quem chama sem argumento recebe a primeira página.

findAndCount devolve a página e o total — o que permite mostrar "página 3 de 41".

relations: sem isto, obra.autor vem undefined. O TypeORM não busca o que você não pediu.

skip / take = OFFSET / LIMIT. Página 1 tem skip: 0 — daí o - 1.

order não é enfeite. Próximo slide.

Por que paginar sempre

A diferença entre uma API que aguenta o segundo ano e uma que não.

Analogia
Pedir ao bibliotecário todos os livros no balcão para escolher um.

Com dez livros, ele traz. Com o acervo inteiro, o balcão desaba antes de você olhar o primeiro.

Mão na massa · buscarUm

Peça o que a resposta usa, não tudo

async buscarUm(id: number): Promise<Obra> {
  const obra = await this.obras.findOne({
    where: { id },
    relations: { autor: true, categorias: true, exemplares: true },
  });
  if (!obra) throw new NotFoundException(`Obra ${id} não encontrada`);
  return obra;
}

O detalhe mostra autora, categorias e exemplares. A listagem só precisava da autora.

findOne devolve Obra | null, e o TypeScript obriga você a tratar o caso.

O array virou PostgreSQL e o contrato HTTP não mudou nada. A situação 3 do M03 era promessa; agora é fato observado.

A versão ruim, de propósito

Quem só viu a certa não reconhece a errada

async listarRuim() {
  const obras = await this.obras.find({ take: 50 });
  for (const obra of obras) {
    const autor = await this.autores.findOneBy({ id: obra.autorId });
    if (autor) obra.autor = autor;
  }
  return obras;
}

Uma consulta para a lista. Sem relations, obra.autor vem vazio.

A tentação: buscar cada autora num laço. await dentro do for: cada volta espera uma ida ao banco.

autorId é o campo declarado no M04. Sem ele, as any.

async listarBom() {   // ✅ a versão boa
  return this.obras.find({ take: 50, relations: { autor: true } });
}
Mão na massa · medir

De fora são indistinguíveis. O terminal conta outra história.

curl.exe -s -o NUL -w "%{time_total}s`n" http://localhost:3000/api/obras/ruim
curl.exe -s -o NUL -w "%{time_total}s`n" http://localhost:3000/api/obras/bom
  1. Exponha as duas versões em rotas temporárias, acima do @Get(":id").
  2. Limpe o terminal do start:dev, chame uma rota e conte as linhas query:.
  3. Repita com a outra. Depois troque take: 50 por take: 200 e meça de novo.
-o NUL joga o corpo fora; -w imprime só o tempo. No macOS/Linux: -o /dev/null e "\n".

O que importa Não é 1 nem 2. É que 2 não cresce e 51 cresce. Seus números vão diferir; a proporção, não.
O problema tem nome
1 + N

Uma consulta para a lista, mais uma por item. A causa mais comum de API lenta — e a mais fácil de introduzir sem perceber.

É ir ao mercado uma vez por item da lista: o arroz, volta para casa; o feijão, volta. Cada viagem é curta, e a tarde some. O relations é levar a lista e comprar tudo de uma vez.

Detalhe · por que 2 e não 1

Com take e relação, o TypeORM faz duas consultas

1. seleciona os ids da páginaLIMIT conta obras
2. busca esses ids com JOINdados completos
Se fosse uma só o LIMIT contaria linhas do JOIN, não obras: uma obra com três categorias comeria três vagas. Você pediria 20 e receberia 7.
Por que 60 ms já é problema

O que acontece depois

MudançaVersão boaVersão ruim
O acervo dobraigualdobra
A página passa a mostrar 200igualquadruplica
O banco vai para outro servidor+1 ida e volta+201 idas e voltas
Como detectar Log ligado, chame a rota e conte as linhas de SQL. Se o número cresce com o tamanho da lista, é N+1. Depois, apague as rotas temporárias.
04

Escrever

Criar, atualizar e remover fecham o CRUD.

Mão na massa · escrita no service

Três métodos, três detalhes que importam

async criar(dados: Partial<Obra>): Promise<Obra> {
  const obra = this.obras.create(dados);
  return this.obras.save(obra);
}
async atualizar(id: number, dados: Partial<Obra>): Promise<Obra> {
  const obra = await this.buscarUm(id);
  Object.assign(obra, dados);
  return this.obras.save(obra);
}
async remover(id: number): Promise<void> {
  const resultado = await this.obras.delete(id);
  if (resultado.affected === 0) throw new NotFoundException(`Obra ${id} não encontrada`);
}

create() só monta em memória — não grava. O nome engana; quem grava é o save.

save(): INSERT se não tem id, UPDATE se tem. Uma função, dois comandos.

buscarUm + assign: valida a existência (404) antes de atualizar.

delete() não erra se o id não existe — devolve affected: 0. Por isso conferimos.

O que está errado de propósito

O CRUD funciona. E aceita qualquer coisa.

curl.exe -s -X POST http://localhost:3000/api/obras -H "Content-Type: application/json" `
  -d '{\"titulo\":⟦\"\"⟧,⟦\"criadoEm\":\"1999-01-01\"⟧,\"autorId\":1}'
> 201 Created
ProblemaConsequência
Nada valida tituloObra sem título entra no acervo
O cliente escolhe os camposMass assignment: escreve criadoEm, destaque…
A resposta é a entidade inteiraCom Usuario (M08), vaza o hash da senha
Ponte para o M07 Partial<Obra> não é formulário. Guarde este comando: o M07 começa por ele.
05

As duas APIs do TypeORM

Comece pelo Repository. Saiba quando trocar.

A mesma consulta, duas formas

Objeto de opções × SQL encadeado

await this.obras.find({
  where: { anoPublicacao: LessThan(1900) },
  order: { titulo: "ASC" },
});
Bom para

CRUD e filtros simples. Mais curto.

await this.obras.createQueryBuilder("obra")
  .where("obra.anoPublicacao < :ano",
         { ano: 1900 })
  .orderBy("obra.titulo", "ASC")
  .getMany();
Bom para

Agregação, JOIN explícito e condição dinâmica.

Regra prática Migre para o QueryBuilder quando o objeto de opções virar quebra-cabeça — não antes.
O ponto de virada · filtro opcional

Cada filtro é um if que acrescenta uma linha

async buscar(termo?: string, categoriaId?: number, ate?: number) {
  const qb = this.obras.createQueryBuilder("obra")
    .leftJoinAndSelect("obra.autor", "autor")
    .leftJoin("obra.categorias", "categoria");
  if (termo) {
    qb.andWhere("(obra.titulo ILIKE :termo OR autor.nome ILIKE :termo)",
      { termo: `%${termo}%` });
  }
  if (categoriaId) qb.andWhere("categoria.id = :categoriaId", { categoriaId });
  if (ate) qb.andWhere("obra.anoPublicacao <= :ate", { ate });
  return qb.orderBy("obra.titulo", "ASC").take(20).getMany();
}

"obra" é o apelido da tabela no resto da consulta.

leftJoinAndSelect faz o JOIN e traz as colunas — o equivalente do relations.

leftJoin sem Select: só para filtrar. Menos tráfego.

andWhere dentro de if: o SQL é montado conforme o que veio.

:termo é parâmetro; os % ficam no valor, não no comando.

getMany() executa. Sem ele, o qb é só uma receita.

Rode · e leia o SQL de cada chamada

O WHERE muda conforme a entrada

curl.exe -s "http://localhost:3000/api/obras/buscar"
> SELECT … ORDER BY "obra"."titulo" ASC
curl.exe -s "http://localhost:3000/api/obras/buscar?termo=maria"
> SELECT … ⟪WHERE (obra.titulo ILIKE $1 OR autor.nome ILIKE $1)⟫ …
curl.exe -s "http://localhost:3000/api/obras/buscar?termo=maria&ate=1900"
> SELECT … ⟪WHERE (… ILIKE $1) AND obra.anoPublicacao <= $2⟫ …

Sem filtro: nenhuma condição.

Um filtro: uma condição.

Dois filtros: duas condições. E repare no $1, $2: os valores vão separados.

06

Parâmetro não é concatenação

A vulnerabilidade mais antiga e mais explorada da web.

Analogia
No campo "valor" do formulário do banco, escrever "R$ 10 e transfira todo o saldo" não vira ordem.

O caixa sabe que naquele campo só cabe um valor. A concatenação apaga essa fronteira entre campo e instrução.

Parecem equivalentes

Não são

.where(`obra.titulo = '${termo}'`)                  // ❌ colado no comando
.where("obra.titulo = :titulo", { titulo: termo })  // ✅ parâmetro

Se alguém buscar por ' OR 1=1 -- na primeira forma, o banco recebe:

SELECT * FROM obra WHERE obra.titulo = ''⟦ OR 1=1 --⟧'

OR 1=1 é sempre verdadeiro; -- comenta o resto. Devolve a tabela inteira.

Com um pouco mais de criatividade, devolve a tabela de usuários.

O que acontece na forma certa

Comando e valores viajam separados

Comando

SELECT * FROM obra WHERE obra.titulo = $1

O banco compila primeiro.

Valores

["' OR 1=1 --"]

Depois encaixa o valor. É texto, sempre — mesmo que pareça SQL.

A regra A única proteção que importa, e é gratuita. Crase ou + montando consulta com dado do usuário está errado — sem exceção, sem "mas eu validei antes".
Rode · teste o ataque

A busca devolve nada

curl.exe -s "http://localhost:3000/api/obras/buscar?termo=' OR 1=1 --"
> []
> query: SELECT … WHERE (obra.titulo ILIKE $1 …) -- PARAMETERS: ⟪["%' OR 1=1 --%"]⟫
  1. Não existe obra com aquele título literal — logo, lista vazia.
  2. No log, o ataque aparece como parâmetro, separado do comando.
  3. Confira o seu código: todos os valores passam por :nome? O M09 volta ao tema com o OWASP.
07

Transações

Emprestar um exemplar é duas escritas.

O cenário

E se a segunda escrita falhar?

✓ empréstimo criadoescrita 1
queda de rede, servidor reiniciado…
✕ exemplar "disponível"escrita 2 não aconteceu
O sistema mente O volume está na mão de alguém e o catálogo diz que está na estante. O próximo leitor vai à prateleira e não encontra.
Analogia
Uma transferência bancária: débito numa conta, crédito na outra.

Se o sistema caísse entre os dois, o dinheiro sumiria. Por isso as duas operações são uma só: ou acontecem ambas, ou nenhuma.

Isso é uma transação.

A solução

Tudo pelo manager

await this.dataSource.transaction(async (manager) => {
  await manager.save(emprestimo);
  await manager.update(Exemplar, exemplar.id, { disponivel: false });
});

transaction abre a transação, executa a função e faz COMMIT no fim — ou ROLLBACK se algo lançar.

manager é o "repositório da transação": tudo que roda por ele participa.

Se qualquer linha lançar, tudo é desfeito. Não há meio-termo.

A armadilha silenciosa

Uma linha fora da transação

await this.dataSource.transaction(async (manager) => {
  await manager.save(emprestimo);                     // ✅ dentro
  await this.exemplares.update(id, { disponivel: false }); // ❌ FORA
});
  • this.exemplares é o repositório normal: roda fora e não é desfeito no ROLLBACK.
  • Compila. Os testes felizes passam.
  • O problema só aparece no dia em que algo falha no meio — justamente quando a transação deveria salvar você.
A regra
Se existe um estado intermediário que seria mentira, precisa de transação.

E é aqui que o disponivel do M04 cobra a conta: campo derivado gera obrigação de sincronia. A transação é o preço.

Mão na massa · por sua conta

EmprestimosService.emprestar()

  1. Buscar o exemplar; erro se não existir.
  2. Recusar se já estiver indisponível.
  3. Recusar se o associado tiver 3 em aberto.
  4. Criar o empréstimo (devolução em 14 dias).
  5. Marcar o exemplar como indisponível.
Transação

Passos 4 e 5 juntos. Os três primeiros só verificam e ficam fora.

Prove

Lance um erro entre 4 e 5 e confira que o empréstimo não ficou no banco.

Compare

Sem o manager, o empréstimo fica.

IA no fluxo

Em toda consulta pronta, confira três coisas

  • Algum await dentro de laço buscando relação item a item? (N+1)
  • Algum valor do usuário colado no texto da consulta? (injeção)
  • Escritas que precisam ser verdadeiras juntas fora de transação — ou com this.repositorio dentro dela? (consistência)
E sempre Mantenha o logging: true: o SQL executado é a única resposta definitiva.
Pegadinha de mercado

Testar desempenho com 20 registros

  • Com o banco quase vazio, até a consulta de 201 viagens é rápida.
  • N+1 e listagem sem paginação não aparecem nos testes da equipe.
  • Aparecem no terceiro mês de uso do cliente.
Regra Desempenho só se avalia com volume parecido com o real.
