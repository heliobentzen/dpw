02

Ler antes de escrever

Quatro arquivos pequenos. O Hello World! sai deles.

Leitura · src/main.ts

Toda a aplicação nasce de um módulo

import { NestFactory } from "@nestjs/core";
import { AppModule } from "./app.module.js";

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(process.env.PORT ?? 3000);
}
await bootstrap();

Sem ./ → um pacote baixado pelo npm, em node_modules.

Com ./ → um arquivo seu. E termina em .js… (já explicamos)

A linha central: monta a aplicação inteira a partir do AppModule.

listen começa a atender HTTP. ?? 3000: se PORT não existir, usa 3000.

await no topo do arquivo — permitido em módulos ESM.

A pergunta que todo mundo faz

Por que .js se o arquivo é .ts?

O TypeScript não reescreve caminhos de import: ele só apaga os tipos. O import aponta para o arquivo que vai existir.

Conceito · decorator

Uma etiqueta colada no código

@Get()   // "responde a GET"
getHello(): string {
  return "Hello World!";
}

npm run start:dev
> [RouterExplorer] Mapped {/, GET} route

Um decorator é uma função que anexa informação a uma classe ou método.

Não executa nem altera o método. Só registra.

Ao subir, o Nest lê as etiquetas e monta a tabela de rotas — é o que o terminal anuncia.

Um mecanismo, vários usos: @Controller, @Entity (M04), @IsString (M07).

Leitura · controller e service

O controller pede; o service sabe

import { Controller, Get } from "@nestjs/common";
import { AppService } from "./app.service.js";

@Controller()
export class AppController {
  constructor(private readonly appService: AppService) {}

  @Get()
  getHello(): string {
    return this.appService.getHello();
  }
}

@Injectable()
export class AppService {
  getHello(): string {
    return "Hello World!";
  }
}

@Controller() marca a classe e define o prefixo de rota (aqui, a raiz).

constructor recebe um AppService já pronto. Guarde esta linha: ela é o assunto da seção 05.

@Get() responde a GET. : string é o tipo de retorno — errar é apontado antes de rodar.

O controller não produz o texto: pede a quem sabe.

@Injectable(): o Nest tem permissão de criar e entregar esta classe.

Leitura · src/app.module.ts

O módulo não faz nada. Ele declara.

@Module({
  imports: [],
  controllers: [AppController],
  providers: [AppService],
})
export class AppModule {}

Seu primeiro endpoint

Um módulo por área do domínio. O do exemplo: pessoas — no projeto, o recurso do cenário principal.

Mão na massa · nest generate

O mais valioso da CLI: os registros

nest generate module pessoas
nest generate controller pessoas --no-spec
nest generate service pessoas --no-spec

module

Cria pessoas.module.ts e o registra em imports do AppModule.

controller

Cria e registra em controllers do PessoasModule.

service

Cria e registra em providers. O --no-spec pula o teste (fica para o M10).

Confira A CLI usou o nome do módulo como rota: @Controller("pessoas"). Se o recurso tiver outro nome, ajuste.
Mão na massa · pessoas.controller.ts

Devolva um valor. O Nest cuida do HTTP.

@Controller("pessoas")
export class PessoasController {
  @Get()
  listar() {
    return [
      { id: 1, nome: "Ana Souza", telefone: "11 90000-0001" },
      { id: 2, nome: "Bruno Lima", telefone: "11 90000-0002" },
    ];
  }
}

"pessoas": todas as rotas desta classe começam em /pessoas.

listar é um nome seu — quem define a URL são os decorators.

Um array comum de objetos JavaScript.

Você não escreveu:

res.json(...) → o Nest converteu

Content-Type: application/json → o Nest pôs

status(200) → padrão do GET

04

Por que separar em camadas

A etapa mais importante do módulo. E é de raciocínio.

O endpoint funciona.
Então por que os dados não podem ficar no controller?

Não é "porque é boa prática". São quatro situações concretas — e todas vão acontecer nesta disciplina.

Analogia

Um restaurante

Controller

O garçom

Anota o pedido, entrega o prato, conversa com o cliente. Fala a língua do salão — o HTTP.

Service

A cozinha

Sabe fazer o prato. Não importa se o pedido veio do salão, do delivery ou do telefone.

E se o garçom cozinhar na mesa? Funciona — até o restaurante precisar de delivery, de um cozinheiro novo ou de dois garçons ao mesmo tempo.
As quatro situações

Onde a lógica no controller cobra a conta

1 · Fora do HTTP

Um script de terminal precisa da lista (M08)

✕ copia-se a lista; uma cópia fica errada em silêncio
✓ o script chama o service

2 · Testar a regra

"No máximo três empréstimos" (M10)

✕ subir servidor, montar requisição, ler status
✓ uma linha, sem servidor

3 · A fonte muda

O array vira PostgreSQL (M04)

✕ o arquivo de rotas vai de 10 para 60 linhas
✓ só o service muda — você confere no M06

4 · Duas pessoas

Uma em rotas, outra em regras

✕ editam as mesmas linhas: conflito
✓ arquivos separados, merge limpo

Situação 2, em detalhe

Separar é o que torna o teste barato

subir a app
montar requisição
enviar
ler resposta
interpretar status

Regra no controller: lento, e quebra por porta ocupada ou rota renomeada.

expect(() => servico.marcar(pessoaComTresEmAberto)).toThrow();

Regra no service: uma linha, sem rede, sem servidor.

Moral Teste caro é teste que ninguém escreve.

05

Injeção de dependência

Como o controller recebe o service — sem fabricá-lo.

Analogia
A geladeira não constrói a usina.

Ela recebe energia pela tomada e não sabe se vem de uma hidrelétrica ou de painéis solares. Trocar a fonte não exige abrir a geladeira.

Injeção de dependência: a classe recebe o que precisa, pronto, pelo construtor. Quem liga os fios é o Nest.

Duas formas

Fabricar × receber

export class PessoasController {
  private pessoas = new PessoasService();
}
Soldado

No teste (M10), não há como trocar o service por um dublê — o new está lá dentro.

A ignorância se espalha

Quando o service precisar do banco, o controller terá de saber montar o banco.

export class PessoasController {
  constructor(
    private readonly pessoas: PessoasService,
  ) {}
}
Declara o que precisa

Não diz como conseguir. Em nenhum lugar existe new PessoasService().

Quem cria é o Nest

Lê o tipo do parâmetro, procura em providers e entrega uma instância pronta.

Por dentro

Como o Nest resolve o construtor

pessoas: PessoasServiceo tipo do parâmetro
procura em
providersdo módulo
cria uma vezsingleton
entrega prontono construtor
Por isso o @Injectable() no service é necessário: sem ele, o Nest não guarda os metadados para criar a classe.
Mão na massa · quebre de propósito

A prova de que a injeção é real

@Module({
  controllers: [PessoasController],
  providers: [⟦/* PessoasService */⟧],
})

> Nest can't resolve dependencies of the PessoasController ⟦(?)⟧.
> Please make sure that the argument PessoasService at ⟦index [0]⟧ is available
> in the ⟦PessoasModule⟧ module.

(?) é a posição do parâmetro que não resolveu.

index [0]: o primeiro parâmetro do construtor.

Onde procurar: a lista providers do PessoasModule. Descomente e o servidor volta.

É o erro mais comum deste módulo e do M04: classe criada e esquecida fora de providers.
O que a injeção traz

Três ganhos práticos

⚡

Teste barato

O teste passa um dublê no lugar do service. Situação 2, resolvida.

①

Uma instância

Criada uma vez e reaproveitada na aplicação inteira.

⇄

Troca sem atrito

Mudar a implementação não toca quem usa. Situação 3 — você comprova no M06.

06

Parâmetros, pipes e erros

Buscar uma pessoa exige ler um pedaço da URL.

Conceito · pipe

O porteiro entre a requisição e o seu método

GET /pessoas/1
ParseIntPipe"1" → 1
buscarUm(1)seu método roda
GET /pessoas/abc
ParseIntPipe"abc" → ?
400 Bad Requestseu método nem é chamado
Pipe converte, valida, ou as duas coisas — antes do seu código. Você não escreve nenhum if.
Mão na massa · rota com parâmetro

Do service à rota

buscarUm(id: number): Pessoa | undefined {
  return this.pessoas.find((p) => p.id === id);
}

@Get(":id")
buscarUm(@Param("id", ParseIntPipe) id: number) {
  return this.pessoas.buscarUm(id);
}

Pessoa | undefined — tipo de união: "ou uma pessoa, ou nada". O tipo diz em voz alta o que o find faz.

":id" — os dois-pontos marcam um trecho variável: /pessoas/1, /pessoas/42…

@Param("id") extrai o pedaço da URL. O nome tem de bater com o do @Get.

ParseIntPipe converte em número antes de o método ser chamado.

Rode · o navegador só mostra o corpo

Veja o status com curl -i

curl.exe -i http://localhost:3000/pessoas/1
> HTTP/1.1 ⟪200 OK⟫
curl.exe -i http://localhost:3000/pessoas/abc
> HTTP/1.1 ⟦400 Bad Request⟧
> {"message":"Validation failed (numeric string is expected)","statusCode":400}

-i mostra os cabeçalhos — o status está na primeira linha.

Esse 400 veio do pipe. Nenhum if, nenhum isNaN, nenhum try.

No macOS e no Linux, escreva curl sem o .exe.

Experimento · tire o pipe
@Param("id") id: number
e chame /pessoas/1. O que acontece?

404 numa pessoa que existe. O id chega como "1" — texto. E "1" === 1 é false.

O : number é TypeScript, e o TypeScript some ao virar JavaScript. Ninguém confere tipos em execução — exceto quem você mandar.

Responder 404

Um 200 vazio é uma mentira

buscarUm(id: number): Pessoa {
  const pessoa = this.pessoas.find((p) => p.id === id);
  if (!pessoa) {
    throw new NotFoundException(
      `Pessoa ${id} não encontrada`);
  }
  return pessoa;
}
O service não…e ainda assim…
importou Responsea resposta saiu certa
escreveu 404o status é 404
montou o JSONo corpo veio padronizado
Ideia Lance em linguagem de domínio ("não encontrada"); o framework traduz para HTTP. O service continua sem saber que HTTP existe.
Armadilha · ordem das rotas

O Nest casa com a primeira que serve

@Get(":id")      // casa com /pessoas/nome
buscarUm(...) {}

@Get("nome")     // nunca alcançada
nome() {}
Resultado

ParseIntPipe("nome") → 400 numa rota que existe.

@Get("nome")     // literal primeiro
nome() {}

@Get(":id")      // parâmetro depois
buscarUm(...) {}
Regra

Rota literal vem sempre antes de rota com parâmetro.

Configuração e documentação

O que muda por instalação fica fora do código. O contrato sai do código.

Configuração fora do código

Dois arquivos, dois papéis

PORT=3000
NOME_ORGANIZACAO=Associação do Bairro

Os seus valores. Secreto.

PORT=
NOME_ORGANIZACAO=

Quais variáveis existem. Público — é por ele que alguém novo sabe o que configurar.

Bug clássico Variável nova no .env sem entrada no .env.example. Só aparece quando alguém clona o projeto.
Mão na massa · ConfigModule

Ler o .env e injetar o valor

imports: [
  ConfigModule.forRoot({ isGlobal: true }),
  PessoasModule,
],

constructor(private readonly config: ConfigService) {}

nomeDaOrganizacao(): string {
  return this.config.get<string>("NOME_ORGANIZACAO")
    ?? "sem nome";
}

forRoot: "configure aqui, uma vez só". Lê o .env na inicialização.

isGlobal: o ConfigService fica disponível em toda a aplicação, sem reimportar.

A mesma injeção da seção 05 — agora com uma classe do próprio framework.

<string> é um genérico: diz ao TypeScript o tipo esperado.

Mão na massa · não subir quebrado

1. Descrever o formato esperado

import { z } from "zod";

export const esquemaEnv = z.object({
  PORT: z.coerce.number().default(3000),
  NOME_ORGANIZACAO: z
    .string("NOME_ORGANIZACAO é obrigatória")
    .min(1, "NOME_ORGANIZACAO não pode ficar vazia"),
});

zod descreve formatos e valida dados em execução: npm install zod.

coerce: variável de ambiente é sempre texto. Converte antes de validar.

Duas mensagens: chave ausente e chave vazia são problemas diferentes.

Mão na massa · não subir quebrado

2. Falhar com uma mensagem legível

export function validarEnv(bruto: Record<string, unknown>) {
  const resultado = esquemaEnv.safeParse(bruto);
  if (!resultado.success) {
    const problemas = resultado.error.issues.map((i) => `  - ${i.message}`);
    throw new Error(`Variáveis de ambiente inválidas:\n${problemas.join("\n")}`);
  }
  return resultado.data;
}

Error: Variáveis de ambiente inválidas:
  - ⟦NOME_ORGANIZACAO é obrigatória⟧

safeParse devolve sucesso ou erro em vez de lançar. Você decide o que fazer.

Uma mensagem legível, com todos os problemas — não o objeto cru do Zod.

Ligue com validate: validarEnv no forRoot. Comente a variável e veja a app não subir.

Por que isso vale uma etapa
Melhor não subir do que subir pela metade.

Serviço que não sobe se resolve em dois minutos lendo a mensagem. Serviço que sobe pela metade falha na frente do usuário — e leva horas para ser rastreado até uma variável faltando.
