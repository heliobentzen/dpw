classes que geram o banco

Você escreve uma classe. O banco cria a tabela.

Pré-requisito: M03 · TypeORM · PostgreSQL · Docker
Item central da ementa: "classes para geração automática do banco de dados". Ritmo: uma ideia por slide. Confirme antes que todos têm Docker funcionando.
A ideia do módulo

Uma classe vira uma tabela

Você escreve
@Entity()
export class Autor {
  @Column()
  nome: string;
}
→
O banco recebe
CREATE TABLE "autor" (
  "nome" varchar NOT NULL
)

Quem faz essa tradução é o TypeORM.

02

O que é um ORM

E por que usar um.

Sem ORM

SQL escrito à mão

const { rows } = await pool.query(
  "SELECT id, titulo FROM obra WHERE id = $1", [id]
);
const obra = rows[0];   // tipo: any

Funciona. Mas o TypeScript não sabe nada sobre obra.

Sem ORM

Três problemas que crescem com o projeto

1

Sem tipo

Erro de digitação compila e quebra em produção.

2

SQL espalhado

A mesma consulta em cinco arquivos.

3

Dois lugares

Tabela no banco, expectativa no código. Podem divergir.

Analogia
O ORM é um intérprete.

Você fala TypeScript. O banco fala SQL. O ORM (Object-Relational Mapper) traduz nos dois sentidos.

Com ORM

A classe vira a única fonte de verdade

class Obra
o tipo do TypeScript
a tabela do banco
a consulta SQL

Os três problemas somem de uma vez.

03

A classe vira tabela

Uma linha de cada vez.

Passo 1 · a tabela

@Entity() transforma a classe em tabela

@Entity()
export class Autor {
}
→
CREATE TABLE "autor" (
)

Sem @Entity(), é só uma classe comum.

Passo 2 · a chave

Todo registro precisa de um número único

@PrimaryGeneratedColumn()
id: number;
→
"id" SERIAL NOT NULL,
PRIMARY KEY ("id")

O banco gera o número sozinho, a cada inserção.

Passo 3 · coluna obrigatória

Por padrão, toda coluna é obrigatória

@Column({ length: 150 })
nome: string;
→
"nome" varchar(150)
  ⟪NOT NULL⟫

length: 150 vira o limite. O NOT NULL você nem pediu — é o padrão.

Passo 4 · coluna opcional

Para aceitar vazio: nullable

@Column({ type: "date",
          nullable: true })
nascimento: string | null;
→
"nascimento" date

Repare: o tipo TypeScript acompanha — string | null.

Passo 5 · valor padrão

Quando ninguém informa: default

@Column({ type: "text",
          default: "" })
biografia: string;
→
"biografia" text
  NOT NULL ⟪DEFAULT ''⟫

text não tem limite de tamanho; varchar(n) tem.

Mão na massa · acervo.module.ts

Avise o módulo que a entidade existe

@Module({
  imports: [TypeOrmModule.forFeature([Autor])],
  ...
})
Atenção Entidade fora do forFeature não existe para o TypeORM.
Rode · olhe o terminal

A tabela nasceu

npm run start:dev
> query: CREATE TABLE "autor" ("id" SERIAL NOT NULL, "nome" varchar(150) ...
docker compose exec db psql -U bibliocom -d bibliocom -c "\d autor"
Deu certo se o \d autor mostra as quatro colunas.

O CREATE TABLE aparece só na primeira vez. Depois a tabela já existe.

04

Cada opção é uma decisão

Modelar é decidir. Digitar é outra coisa.

Antes de escrever um @Column

Cinco perguntas

  • type — que tipo de dado é?
  • length — qual o tamanho máximo?
  • nullable — pode não existir?
  • unique — pode repetir?
  • default — o que vale se ninguém informar?
A decisão mais cara
Toda coluna nullable obriga o código a perguntar "e se for nulo?"

Em todo lugar que lê essa coluna. Para sempre.

Compare

Quando o nulo faz sentido?

nascimento

nullable ✓

Nulo quer dizer "não sabemos a data". Faz sentido.

biografia

default: "" ✓

Texto vazio já quer dizer "sem biografia". Nulo seria repetir.

A regra
Nulo só quando ele significa algo.

Texto opcional? Use default: "".

Exercite · 1 de 2

Qual @Column?

CPF do associado

length: 11, unique: true

Obrigatório e não pode repetir.

Valor da multa

type: "decimal"

Nunca float para dinheiro: ele perde centavos.

Deixe a turma responder antes de revelar.
Exercite · 2 de 2

Qual @Column?

Data da devolução

type: "date", nullable: true

Aqui o nulo significa algo: "ainda não devolveu".

Aceita avisos por e-mail

type: "boolean", default: true

Sempre tem valor. O padrão é decisão da biblioteca.

O ciclo do módulo

Três movimentos, sempre

1. Muda a classe
2. Olha o SQL
3. Confere o banco
Experimente

Uma coluna nova, sem SQL

@Column({ length: 60,
          default: "" })
nacionalidade: string;
→
ALTER TABLE "autor"
  ADD "nacionalidade"
  varchar(60)

Salvou, o banco mudou. É o outro item da ementa: atualizar o banco a partir das classes.

Relações

Como uma tabela aponta para outra.

Relação 1:N

Uma autora, muitas obras

Regra A coluna que aponta (autorId) fica do lado "muitos" — na obra.
Em código · obra.entity.ts

"Muitas obras para uma autora"

@ManyToOne(() => Autor, (autor) => autor.obras)
autor: Relation<Autor>;

@ManyToOne cria a coluna autorId e a chave estrangeira.

Relation<Autor>: a obra "conhece" sua autora. O Relation é explicado já, já.

Em código · obra.entity.ts

Declare também o autorId

@Column()
autorId: number;

A coluna já existia no banco. Declarar dá tipo a ela no TypeScript — e o M06 vai usá-la.

Em código · autor.entity.ts

O outro lado: @OneToMany

@OneToMany(() => Obra, (obra) => obra.autor)
obras: Relation<Obra[]>;
Detalhe Este lado não cria coluna. Só permite navegar da autora até as obras.
Por que Relation<>?

O problema do ovo e da galinha

obra.entity.ts
precisa de Autor
autor.entity.ts
precisa de Obra
obra.entity.tsainda carregando…
Sem Relation A API nem sobe: Cannot access 'Autor' before initialization
A regra prática
Propriedade de relação? Use Relation<>.

@ManyToOne, @OneToMany, @ManyToMany. Coluna comum não precisa.

Exercite

Responda antes de revelar

A coluna se chama autorId. Por quê?Nome da relação + Id
@OneToMany criou coluna em autor?Não, só navega
Se apagar @Column() autorId, a coluna some?Não, o @ManyToOne a cria
Uma pergunta de negócio
Alguém apaga a autora.
E as obras dela?

Quem responde é a opção onDelete.

onDelete

Três respostas possíveis

RESTRICT

Impede

Não deixa apagar enquanto houver obras.

CASCADE

Apaga junto

Some a autora, somem as obras.

SET NULL

Desvincula

A obra fica, sem autora.

Como decidir
"Este registro faz sentido sozinho?"
Obra sem autora?

Faz sentido.

→ RESTRICT

Exemplar sem obra?

Não faz.

→ CASCADE

Cuidado
"Usei CASCADE para o erro sumir" não é justificativa.

O erro estava lá para avisar que você ia apagar algo importante.

Relação N:N

Muitas obras, muitas categorias

obra
obra_categoriaobraId · categoriaId
categoria

Nenhum dos lados consegue guardar a ligação. Nasce uma terceira tabela.

Em código · obra.entity.ts

@ManyToMany + @JoinTable

@ManyToMany(() => Categoria, (c) => c.obras)
@JoinTable({ name: "obra_categoria" })
categorias: Relation<Categoria[]>;

@ManyToMany vai nos dois lados.

@JoinTable vai em um lado só — é ele que cria a tabela do meio.

Obra × exemplar

Um livro no catálogo, três na estante

Dom Casmurroobra · o catálogo
Volume 1exemplar · tombo 0001
Volume 2exemplar · tombo 0002
Volume 3exemplar · tombo 0003
Em código · exemplar.entity.ts

Duas decisões do exemplar

@Column({ length: 20, unique: true })
tombo: string;

@Column({ type: "enum", enum: EstadoExemplar })
estado: EstadoExemplar;

unique: dois volumes com o mesmo tombo é erro de cadastro.

enum: só valores da lista (novo, bom, desgastado, descartado). Nada de "Bom" e "bom".

Em código · exemplar.entity.ts

Exemplar não existe sem obra

@ManyToOne(() => Obra, (o) => o.exemplares,
           { onDelete: "CASCADE" })
obra: Relation<Obra>;

Aqui o CASCADE é legítimo: apagou a obra, os volumes dela não fazem sentido.

Índices
Sem índice, o banco lê a tabela inteira.

Como procurar um assunto num livro sem índice remissivo: página por página.

Em código · obra.entity.ts

Um @Index no que é muito buscado

@Index()
@Column({ length: 13, default: "" })
isbn: string;
Regra Indexe o que é buscado com frequência. O balcão busca ISBN o dia inteiro.
Índice tem preço

Não indexe tudo

Espaço

Cada índice ocupa disco.

Escrita

Cada INSERT atualiza todos os índices.

Já existe

Chaves primária e estrangeira já vêm indexadas.

06

Onde o atalho quebra

O synchronize com dados de verdade no banco.

Experimento 1

Encurtar uma coluna com texto dentro

> ALTER TABLE "autor" ⟦DROP COLUMN "biografia"⟧
> ALTER TABLE "autor" ADD "biografia" varchar(10)
Resultado

O texto sumiu.

Sem erro. Sem aviso. A aplicação subiu normalmente.

Experimento 2

Renomear uma coluna

> ALTER TABLE "obra"
>   ⟪RENAME COLUMN "sinopse" TO "resumo"⟫
Resultado

O dado sobreviveu.

Ele adivinhou certo — desta vez.

Desfaça os dois experimentos antes de seguir.
A lição
O problema é não saber qual dos dois vai acontecer.

No M05, você vai ler cada mudança antes de ela rodar.

Mão na massa · por sua conta

Modele o empréstimo

  • Associado: nome, e-mail único, data de inscrição.
  • Empréstimo: um exemplar + um associado + três datas.
  • Apagar associado com empréstimo aberto: não pode.
  • Apagar exemplar emprestado: não pode.
Mão na massa · o que entregar

Código e justificativa

  1. As entidades Associado e Emprestimo.
  2. O registro no forFeature.
  3. A conferência com \d emprestimo.
  4. Uma frase justificando cada nullable, unique e onDelete.
Dica Empréstimo tem dois @ManyToOne.
O outro lado da moeda

O que o ORM cobra

  • Você escreve menos SQL — e pode entender menos SQL.
  • Consultas ingênuas ficam lentas sem avisar (M06).
  • Casos difíceis ainda pedem SQL (M06).
Por isso o logging: true fica ligado: leia o SQL que ele gera.
Pegadinha de mercado

nullable: true "por precaução"

Parece prudente. Na prática, espalha if (x === null) pelo sistema inteiro.

Padrão Obrigatório. Nulo é exceção, com motivo.
IA no fluxo

A IA escreve a sintaxe. A decisão é sua.

Erro comum

nullable em tudo

Erro comum

Erro comum

Resumo

Cinco ideias para levar

  • Uma classe com @Entity vira uma tabela.
  • Toda coluna é obrigatória, a menos que você diga o contrário.
  • Nulo só quando significa algo.
  • A chave estrangeira fica do lado "muitos".
  • onDelete é decisão de negócio.
Desafio de fixação

Multa por atraso

R$ 0,50 por dia, até R$ 10,00. Uma coluna em Emprestimo ou uma entidade própria?

  1. Dá para pagar em parcelas?
  2. A coordenação pode perdoar?
  3. O valor da diária pode mudar no futuro?
